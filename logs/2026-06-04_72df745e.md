Here are the replicable innovations from each, drawn from their pathway pages. I've separated genuine cross-use-case innovations from context-specific ones.

## From MahaVistaar

**1. Dual-provider inference topology ("latency over queue depth")**
Self-hosted fine-tuned model as primary (vLLM, capped at 100 concurrent calls), cloud API as instant fallback when the cap saturates — no queuing. This delivered a ~180× cost reduction (₹9.4/question on Azure → ₹0.05/question self-hosted) while guaranteeing users never experience queuing latency. Replicable across any voice or chat AI deployment at scale where cost and reliability both matter.

**2. Decoupled moderation layer**
An independent moderation model (GPT-OSS Safeguard 20B) fully separated from the advisory model, doing domain validation, safety filtering, and prompt-injection defence on every query — moderation-before-output, not review-after-complaint. Replicable in any safety-sensitive use case (health, finance, eligibility advice).

**3. Connect-to-data-where-it-lives architecture**
The orchestrating agent pulls from institutional databases at query time and sends only the prompt to the LLM — raw data never leaves government systems. Replicable wherever data sovereignty, inter-departmental ownership, or DPDP-type compliance is a constraint.

**4. Categorise by user mental model, not org chart**
Grouping use cases by what the user is trying to do (asking about a sick crop, checking eligibility) rather than by departmental taxonomy. Replicable across any multi-service citizen-facing system.

**5. Query log as institutional feedback loop**
205,000+ monthly queries become a visible, quantified demand signal for knowledge gaps the institution didn't know it had. Replicable as a governance-as-learning mechanism in any advisory system.

## From Blue Dots AI

**1. Build the data through the interaction itself**
Neither side existed digitally before deployment — Blue Dots are created by participants at the moment of a 2–3 minute consent-based voice call. This sidesteps the "wait for clean data" trap entirely. Highly replicable for any use case where the supply or demand side is informal and digitally dark (welfare discovery, local services, informal markets).

**2. Participant-owned data as architecture, not policy**
Citizens can update, pause, or delete their own Blue Dot; ownership is built into the architecture rather than promised in a privacy notice. Replicable wherever consent and erasability are required by design.

**3. Aggregator-driven mass onboarding**
One MSME association onboarded 300+ employers in two weeks; one ITI onboarded 500+ seekers. Using existing institutions as enrolment multipliers rather than acquiring users one by one. Replicable in any cold-start network where intermediaries already aggregate the target population.

**4. The facilitation team as a designed role**
A 6–8 person team whose job is rhythm and coordination (not technology) — explicitly designed to keep the network from going stale and to provide continuity when champions rotate. Replicable in any multi-stakeholder deployment that depends on sustained momentum rather than a one-time launch.

**5. Status tracking with staleness nudges**
The Aggregator DPG tracks each signal as active/at-risk/satisfied/stalled and auto-nudges when profiles go cold — addressing the documented primary operational risk (stale data eroding both-side confidence). Replicable in any two-sided matching system.

## Shared across both (the strongest replicable pattern)

**Voice-as-inclusion as a design constraint, not a feature** — 2–3 minutes, any phone, any language, no literacy required. Both treat this as foundational architecture. The wiki flags this as a candidate synthesis pattern appearing across four deployments (MahaVistaar, Blue Dots, Amul, Ethiopia).
